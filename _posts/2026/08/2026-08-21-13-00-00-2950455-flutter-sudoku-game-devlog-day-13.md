이 기록의 핵심은 숫자판을 화면에 그리는 일이 아니라, 플레이어가 한 판을 중간에 포기하지 않고 자기 판단으로 끝낼 수 있게 만드는 Flutter 게임의 기준이다.

스도쿠 프로젝트 13일 차다. 기능은 같으니 Material 위젯만 쓰면 된다고 생각했다. iPhone에서 뒤로 가기 제스처와 다이얼로그 순서가 낯설게 느껴졌다. 처음엔 작은 퍼즐 게임이니 화면 몇 장과 리스트 하나면 끝날 줄 알았다. 해보니 화면에 보이지 않는 규칙과 예외가 더 오래 남았다. 숫자 하나를 넣는 행동에도 고정 칸인지, 같은 줄에 중복이 생겼는지, 메모인지 확정인지가 따라붙는다. 그중 하나라도 흐릿하면 플레이어는 앱이 틀렸다고 느낀다.

## 오늘의 판단

게임 보드는 공통으로 두되 설정과 확인 흐름은 플랫폼 관례를 따랐다. 이 기준을 세운 뒤에는 기능을 추가할 때마다 “이 변화가 한 판을 더 편하게 풀게 하는가”를 먼저 물었다. 멋있어 보이지만 답하지 못하는 기능은 메모에만 남겼다. 실제 게임을 계속 열어 보는 사람이라면 이 우선순위가 꽤 현실적이라는 걸 금방 안다. 도중에 방향을 바꾸는 비용도, 처음 기준 없이 쌓은 코드를 고치는 비용보다 훨씬 작았다.

![행과 열, 3×3 박스를 함께 확인하는 스도쿠 보드](https://images.unsplash.com/photo-1518546305927-5a555bb7020d?auto=format&fit=crop&w=1200&q=80)

이 이미지에서 봐야 할 부분은 81칸의 밀도보다 선택한 한 칸과 주변 정보가 어떤 단서로 분리되는지다.

## 구현하면서 막힌 지점

스도쿠는 규칙이 단순해서 더 방심하기 쉽다. 1부터 9까지의 숫자만 다루면 되니 모델도 간단할 것 같았지만, 게임 상태에는 선택 셀, 고정 여부, 메모, 경과 시간, 되돌리기 기록, 힌트 사용 수가 계속 붙는다. 오전에는 빠르게 붙인 코드가 저녁에는 저장과 복구를 막았다. 그래서 화면 이벤트가 리스트를 직접 바꾸지 않게 하고, 입력은 하나의 변경 함수로 모았다.

오늘의 핵심은 이런 작은 경계다. UI가 아니라 규칙을 먼저 표현하기 위해 검사를 화면 밖에 두었다.

```dart
bool canPlace(List<int> board, int index, int value) {
  if (value < 1 || value > 9) return false;
  final row = index ~/ 9;
  final col = index % 9;
  for (var i = 0; i < 9; i++) {
    if (board[row * 9 + i] == value && i != col) return false;
    if (board[i * 9 + col] == value && i != row) return false;
  }
  final startRow = row - row % 3;
  final startCol = col - col % 3;
  for (var r = startRow; r < startRow + 3; r++) {
    for (var c = startCol; c < startCol + 3; c++) {
      if (board[r * 9 + c] == value && r * 9 + c != index) return false;
    }
  }
  return true;
}
```

코드만 보면 짧다. 실제로는 이 한 덩어리 주변에 입력 불가 조건, 선택 효과, 저장 시점, 테스트 케이스가 붙는다. 특히 고정 숫자를 수정할 수 있게 두는 버그는 자동 테스트가 없으면 손으로 한두 판 풀다가 놓치기 쉽다. 개발 중에는 정상 입력뿐 아니라 빈 칸 선택, 잘못된 숫자, 앱 재실행, 큰 글자 설정을 번갈아 확인했다. 보기 좋게 정리한 화면보다 이 반복에서 잡히는 문제가 더 많았다.

## 확인 기준

| 확인 항목 | 내가 본 기준 | 남긴 이유 |
|---|---|---|
| 한 판 시작 | 3초 안에 보드와 숫자 패드를 이해할 수 있는가 | 첫 이탈을 줄이기 위해서다 |
| 입력 피드백 | 선택·충돌·고정 칸을 색 외의 단서로도 알 수 있는가 | 실수의 원인을 분명히 하려고 했다 |
| 중단 후 복귀 | 앱을 나갔다 와도 진행이 납득 가능하게 남는가 | 퍼즐은 끊겨도 이어 풀기 때문이다 |
| 테스트 | 규칙 오류를 화면 보기 전에 잡는가 | 수동 확인의 빈틈을 줄이기 위해서다 |

오늘은 기능 수를 세지 않았다. 보드에서 숫자를 하나 넣고, 실수했을 때 왜 안 되는지 이해되고, 다시 이어서 풀 수 있는지 세 번씩 확인했다. 이 단순한 반복에서 어색한 부분이 가장 잘 드러났다. 한 번에 많은 것을 완성하려 하면 이런 감각을 놓치기 쉽다. 반대로 하루에 한 가지 판단만 남기면 다음날의 수정 범위가 작아져서, 코드는 조금씩 단단해졌다.

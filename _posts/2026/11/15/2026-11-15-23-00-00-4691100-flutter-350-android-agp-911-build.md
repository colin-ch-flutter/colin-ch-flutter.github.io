이 그림에서 봐야 할 부분은 Dart 코드가 아니라 Flutter·AGP·Gradle·Java가 한 줄의 출시 경로로 묶인다는 점이다.

Flutter 3.50으로 올린 뒤 Android release 빌드가 `Your project's Android Gradle Plugin version ... is lower than ... 9.1.1`에서 멈춘다면 `flutter clean`을 반복할 문제가 아니다. 기존 프로젝트의 AGP를 최소 9.1.1로 올리고 Gradle과 Java도 함께 맞추는 선택이 정석이다. 당장 CI를 복구해야 할 때는 `--android-skip-build-dependency-validation`으로 검사를 건너뛸 수 있지만, 출시 기준으로 남기면 안 된다. Android 빌드가 없거나 Flutter 3.47 이하로 고정된 프로젝트에는 이 오류가 바로 생기지 않는다.

## 왜 갑자기 CI에서만 멈추는가

Flutter 3.50은 2026년 11월 11일 stable로 나왔고, 새 Android 프로젝트는 AGP 9.3.1, Gradle 9.5.0, Java 17 조합을 사용한다. 반면 오래된 프로젝트나 `channel: stable`만 지정한 CI는 서로 다른 SDK를 사용할 수 있다. 내 컴퓨터는 3.47인데 CI가 먼저 3.50을 받은 상황이면 코드 변경 없이도 Gradle 플러그인 적용 단계에서 실패한다.

| 확인 대상 | 출시 기준으로 볼 값 | 놓치기 쉬운 지점 |
|---|---:|---|
| Flutter | 3.50.0 | 로컬과 CI 버전이 다름 |
| Android Gradle Plugin | 9.1.1 이상 | `settings.gradle(.kts)` 또는 오래된 `build.gradle`에 분산됨 |
| Gradle wrapper | 9.5.0 권장 | AGP만 올리면 wrapper가 낮을 수 있음 |
| Java | 17 이상 | Android Studio 내장 JDK와 CI `JAVA_HOME`이 다름 |

Flutter 공식 발표의 새 프로젝트 기본값은 AGP 9.3.1과 Gradle 9.5.0이다. Android Studio 공식 표에서도 API 37에 필요한 최소 AGP는 9.1.1로 안내한다. 따라서 9.1.1은 급한 기존 프로젝트를 살리는 최소선이고, 새 프로젝트 설정을 그대로 맞출 수 있다면 9.3.1 조합을 검토하면 된다.

## 먼저 실제 버전을 출력한다

수정 전에 로컬과 CI에서 같은 명령을 실행해 버전 차이를 기록해야 한다.

```bash
flutter --version
java -version
./gradlew --version
rg 'com.android.application|com.android.tools.build:gradle' android
rg 'distributionUrl' android/gradle/wrapper/gradle-wrapper.properties
```

최근 템플릿은 `android/settings.gradle.kts`의 plugins 블록에 버전이 있다.

```kotlin
plugins {
    id("com.android.application") version "9.1.1" apply false
}
```

오래된 프로젝트라면 `android/build.gradle`의 classpath를 바꿔야 한다.

```groovy
dependencies {
    classpath 'com.android.tools.build:gradle:9.1.1'
}
```

AGP를 9.1.1로 올렸는데 wrapper가 9.3.1보다 낮다면 `android/gradle/wrapper/gradle-wrapper.properties`의 `distributionUrl`도 확인한다. Flutter 3.50 새 프로젝트와 같은 기준을 택한다면 Gradle 9.5.0과 Java 17을 함께 사용한다. 플러그인 중 AGP 9의 built-in Kotlin을 아직 지원하지 않는 것이 있으면 전체 업그레이드 전에 해당 플러그인의 호환 버전을 확인해야 한다.

## 오늘 출시해야 할 때의 우회

검사만 통과시키는 임시 명령은 다음과 같다.

```bash
flutter build appbundle --release \
  --android-skip-build-dependency-validation
```

이 옵션은 AGP 버전을 올려 주지 않고 Flutter의 사전 검증만 끈다. 그래서 AAB가 만들어져도 plugin API, Gradle task, R8, 서명 단계가 안전하다는 뜻은 아니다. 내부 테스트 트랙에 올려 설치·실행·로그인·네이티브 플러그인 호출까지 확인하는 동안에만 사용한다. CI가 갑자기 깨진 날에는 Flutter 버전을 3.47.x처럼 고정해 배포를 잠시 멈추지 않게 할 수 있지만, 고정은 업그레이드를 미루는 방법이지 해결은 아니다.

## 출시 전 체크리스트

- [ ] 로컬과 CI의 `flutter --version`, Java, Gradle 출력이 기록돼 있다.
- [ ] AGP가 9.1.1 이상이고, 설정 파일에 오래된 AGP 선언이 하나 더 남아 있지 않다.
- [ ] Gradle wrapper와 Java 17 조합으로 `flutter build appbundle --release`를 실행했다.
- [ ] AGP 9를 지원하지 않는 Flutter 플러그인을 찾아 업데이트 또는 교체 판단을 했다.
- [ ] 우회 플래그 없이 내부 테스트 트랙 설치본을 실행했다.

핵심은 Flutter 3.50 오류를 `clean` 명령으로 지우는 것이 아니라 빌드 도구의 최소선과 새 프로젝트 기준을 구분하는 데 있다. 오늘 배포를 위해 검사를 건너뛸 수는 있지만, 다음 빌드에서 같은 오류가 재발하지 않게 하려면 AGP 9.1.1 이상·Gradle 9.5.0·Java 17을 CI에 명시하고 플러그인 호환성까지 확인해야 한다.

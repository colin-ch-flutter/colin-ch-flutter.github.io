![Flutter Android 16 API 36과 16KB 페이지 크기 출시 점검](/images/2026-09-16-flutter-android16-16kb-release.png)

2026년 9월에 Google Play에 Flutter 앱을 업데이트한다면 `targetSdk 36`을 기준으로 빌드하고, native `.so` 파일을 포함한 앱은 16KB 페이지 크기 호환성까지 확인해야 한다. 순수 Dart·Kotlin·Java 앱이라면 16KB 대응 작업을 따로 하지 않아도 될 가능성이 높지만, FFI·카메라·지도·데이터베이스·Firebase 플러그인을 쓰는 앱은 아래 검사를 건너뛰면 안 된다.

## 지금 출시가 막히는 두 조건

Google Play 공식 기준에 따르면 2026년 8월 31일부터 새 앱과 업데이트는 Android 16(API 36) 이상을 타깃으로 제출해야 한다. 기존 앱이 새 Android 사용자에게 계속 노출되기 위한 기준은 API 35다. 별도 연장 신청을 했다면 2026년 11월 1일까지 시간을 벌 수 있지만, 빌드 검증 자체가 끝난 것은 아니다.

또 Android 15(API 35) 이상을 대상으로 하는 64비트 앱은 16KB 메모리 페이지를 지원해야 한다. 공식 문서에 적힌 Google Play 업데이트 제한일은 2027년 2월 1일이다. API 36으로 올렸다고 해서 모든 플러그인의 native 바이너리까지 자동으로 고쳐지는 것은 아니다.

| 점검 항목 | 확인할 값 | 적용되지 않을 수 있는 경우 |
|---|---|---|
| Play 제출 타깃 | `targetSdk = 36` | Wear OS·Automotive·TV 등은 별도 기준 |
| 컴파일 SDK | `compileSdk = 36` | 낮은 SDK를 반드시 써야 하는 구형 플러그인 |
| 16KB 정렬 | 모든 native `.so` | native 코드가 전혀 없는 앱 |
| 실제 동작 | 16KB 에뮬레이터 실행 | Java/Kotlin만 쓰는 앱도 회귀 확인 권장 |

그림에서 볼 부분은 버전 숫자보다 Flutter 빌드 결과에 포함된 native 라이브러리와 정렬 검사 단계다.

## Gradle에서 API 36을 고정한다

Flutter 프로젝트의 `android/app/build.gradle` 또는 `build.gradle.kts`에서 현재 템플릿 구조에 맞게 값을 확인한다. 아래는 Groovy 형식의 예시다.

```gradle
android {
    namespace "com.example.home"
    compileSdk 36

    defaultConfig {
        applicationId "com.example.home"
        minSdk 24
        targetSdk 36
    }

    // 16KB 대응이 필요한 native 의존성이 있을 때만 명시적으로 고정한다.
    ndkVersion "28.2.13676358"
}
```

Flutter 템플릿이 `compileSdk = flutter.compileSdkVersion`, `targetSdk = flutter.targetSdkVersion`, `ndkVersion = flutter.ndkVersion` 형태라면 무조건 숫자를 덮어쓰지 말고 Flutter SDK·AGP 조합부터 확인한다. Android 공식 문서는 AGP 8.5.1 이상과 NDK r28 이상, 16KB 호환 prebuilt dependency 조합을 기본 경로로 안내한다. 오래된 프로젝트에서 AGP만 올리면 Gradle wrapper, Kotlin 플러그인, JDK 버전이 함께 충돌할 수 있다.

```bash
flutter doctor -v
flutter pub deps --style=compact
flutter clean
flutter pub get
flutter build appbundle --release
```

## 문제를 만드는 플러그인을 찾는 방법

APK Analyzer에서 `lib/arm64-v8a/*.so`와 `lib/x86_64/*.so`를 확인한다. Flutter 엔진만 보인다고 끝내지 말고, `sqlite`, `realm`, `tflite`, `ffmpeg`, `webview`, FFI 계열처럼 native 코드를 끌고 오는 의존성을 `pubspec.lock`과 함께 대조한다.

AAB가 생성된 뒤에는 bundletool로 압축 정렬 정보를 확인한다. `PAGE_ALIGNMENT_16K`가 보여야 16KB zip 정렬을 요청한 번들이다.

```bash
bundletool dump config \
  --bundle=build/app/outputs/bundle/release/app-release.aab \
  | grep alignment
```

특정 플러그인이 계속 경고를 내면 앱 코드에서 임시 플래그를 추가하기보다 플러그인의 최신 버전과 릴리스 노트를 확인한다. 업데이트가 불가능한 native SDK라면 해당 플러그인을 제거한 임시 빌드를 만들어 경고가 사라지는지 비교하는 방식이 원인 분리에 유효하다. 다만 이 비교는 진단용이며, 기능을 빼고 출시하는 해결책은 아니다.

## 에뮬레이터에서 런타임까지 확인한다

Android Studio SDK Manager에서 16KB 페이지 크기를 지원하는 Android 15 시스템 이미지를 설치하고 테스트한다. 실행 중인 기기에서 실제 페이지 크기를 확인한 뒤, 앱 시작·로그인·native 기능 호출·백그라운드 복귀를 점검한다.

```bash
adb shell getconf PAGE_SIZE
# 16384가 나오면 16KB 환경
adb logcat -c
adb logcat | grep -E "FATAL EXCEPTION|UnsatisfiedLinkError|dlopen"
```

네이티브 라이브러리가 4KB 가정으로 `4096`을 하드코딩했거나 `mmap()` 정렬을 직접 계산하는 경우에는 빌드가 성공해도 실행 중 문제가 난다. 이 코드는 앱 Dart 레이어가 아니라 해당 SDK나 플러그인의 Android native 소스에서 고쳐야 한다.

## 출시 전 체크리스트

- [ ] Play Console 제출 대상이 일반 Android 앱인지 Wear OS·TV 등 예외인지 확인했다.
- [ ] `compileSdk`와 `targetSdk`가 36이고, CI에서도 같은 Gradle 파일을 사용한다.
- [ ] `flutter pub deps`로 native 코드를 포함할 가능성이 있는 플러그인을 표시했다.
- [ ] AAB의 alignment 결과와 APK Analyzer의 `.so` 목록을 보관했다.
- [ ] 16KB 에뮬레이터에서 앱 시작과 native 기능을 실행했다.
- [ ] API 36 일반 에뮬레이터에서 edge-to-edge, 키보드, 시스템 뒤로가기를 별도로 확인했다.
- [ ] 실패한 플러그인은 버전 업·교체·제거 중 선택 근거를 기록했다.

핵심은 `targetSdk 36` 변경을 단순 숫자 수정으로 끝내지 않는 것이다. native 라이브러리가 없는 앱은 빌드 설정과 기본 회귀 테스트에 집중하면 되고, native 의존성이 있는 앱은 AAB 정렬과 16KB 런타임을 출시 승인 조건에 넣어야 한다. 무료인 Android Studio APK Analyzer와 에뮬레이터만으로 1차 판별할 수 있으므로, 이 문제 때문에 곧바로 유료 디바이스 클라우드를 구매할 필요는 없다.
